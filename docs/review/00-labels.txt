===============================================================================
BALL / SOCKET MISALIGNMENT — FOURTH REPORT, NOW STRUCTURALLY IMPOSSIBLE
===============================================================================
Time-series probe after removal (scripts/_ball-timeseries.mjs), 18 VERIFIED
deploys, sampling every frame:

    frames with a VISIBLE ball off its slot: 0

That is a real zero, not an unfired-stimulus zero — the probe asserts its deploys
landed (18 landed, 0 skipped) precisely because an earlier version of it reported
"no bug" while nothing had actually fired.

The reason it is now zero is structural rather than tuned. The ONLY code that
could move a ball independently of its socket was the merge sequencer, and the
refill drop-in animation lived INSIDE it as its 'fill' phase — it never ran except
as the tail of a merge cascade. With the sequencer gone, the whole slot-animation
API became unreachable and was deleted with it:

  Shooter3D:       setSlotAnimLock, setSlotScale, setSlotWorldXYZ,
                   resetSlotTransform, getSlotBaseWorld, getSlotWorldPosition,
                   clearAllAnimLocks, and the _animLock field + its skip branches
  GameRenderer3D:  lockBombSlot, setBombSlotScale, setBombSlotWorld,
                   getBombSlotWorld, getBombSlotBaseWorld, resetBombSlot,
                   clearBombAnimLocks, getBombSlotScreenXY

A ball's position is now written in exactly one place — setLaneCount, from
bombSlotZ(row), the same canonical function the Pixi socket derives from. There is
no longer any code path that can put a ball anywhere other than its socket, so the
two cannot disagree by construction. Four incremental fixes failed at this; the
fifth was not another fix, it was deleting the thing that moved the ball.

Cost, stated plainly: refilling bombs no longer animate in, they appear. The
drop-in polish went with the mechanic that owned it. If that reads as abrupt in
play, re-adding it should be a deliberate decision with the socket-derived
positioning discussed below — not a revival of the old independent animator.

===============================================================================
SIM BALANCE — NO SHIFT, AND THE REASON MATTERS
===============================================================================
The 40-level table after removal is BYTE-IDENTICAL to before it. Not "close" —
identical, including the three flagged levels (L4 95.3%, L30 37.0%, L39 58.0%).

SimulationRunner never modelled merging at all. It has no peekMerges /
evaluateMerges / isMerged reference anywhere; the balance bands were always
measured on merge-free play. So the sim needed no change and no level needs a
retune from this.

Worth noting for the record: this means the sim and the live game had DIVERGED for
any player who used merging, and removing the mechanic brings live behaviour back
in line with what the balance gate has always been measuring.

===============================================================================
DELIBERATELY KEPT — do not mistake these for leftovers
===============================================================================
- QUEUE REORDER and BENCH-RETURN survive untouched. They were gated behind a flag
  named `_mergeEnabled` because setting up merges was their original purpose, but
  they are independent mechanics. The flag is now `_reorderEnabled`; the L5 unlock
  and both behaviours are unchanged, and the removal guard asserts they still work
  so a future cleanup cannot delete them by association.
- projection.QUEUE_CLEARANCE_MARGIN (1.22) — this WAS MERGE_SCALE, the worst-case
  bomb radius the queue-fit solver and breach clearance were sized against. The
  VALUE IS UNCHANGED on purpose: dropping it to the now-true 1.0 would let the
  solver grow every bomb, which is a size/FIT decision for the owner, not a side
  effect of deleting a mechanic. Recorded with the queue-depth question in
  THREE_LANE_REDESIGN_BATCH.md §8.
