The KILLS were already correct and have been all along. Verified again here through
the real input path (a real click on the real BOMB button, then a real click on a
real car — no programmatic fire): tapping lane 0 killed 2/2 cars in lane 0, and the
WITNESS car in lane 1 on the SAME ROW survived, as did all of lane 2.

What was never converted is the BLAST. Git history is unambiguous:
  - 20593cd  "fix: BOMB booster clears entire ROW ... via tap Y->row"
      the VFX was authored here, for a bomb that really did clear a row
  - the lane-clear change converted the kill model
  - bd2348d  "test: pin BOMB to lane-only"
      touched SimulationRunner.js and two test files. NO renderer files.
  - Particles3D.spawnBombExplosion has not changed since 888e415, long before.

So the row-shaped explosion is the ORIGINAL row-clear visual, simply left behind.
Its docstring still said so in plain text: "Covers all 4 lanes with a wide
shockwave + concussion freeze ring."

Root cause, upstream of both effects: GameLoop.placeBombOnLane called
    this._onBombExplode(car.position, 1)
`position` is a ROW scalar. The LANE was never passed, so no downstream effect
could draw itself in the right place even in principle:
  - Particles3D looped every lane, 80ms apart, left to right (the sweep)
  - Road3D's ring was centred at x=0, road centre, and grew to radius 3.0 world
    units on a lane only 4.0 wide

Fix: thread the lane through, then bound every element to it — one lane's burst,
ring and light flashes centred on laneToX(lane), radius CELL/2 instead of 3.0/6.3.

SEPARATE — the "can't put another one next to him" report (NO CODE CHANGED)
===============================================================================
Confirmed: deploys are turn-based, one shot at a time, and this is enforced twice
with the two guards DISAGREEING.

  DragDrop.js:394   if (this._firingSlots[laneIdx]) snapBack()   <- SAME lane only
  GameLoop.js:108   if (ANY firingSlot is set) return            <- bare return

Measured: deploy(col0,lane0) is accepted (slot 0 taken, column 3->2); then
deploy(col1,lane1) and deploy(col2,lane2) during that flight are BOTH refused,
with no slot taken and no bomb consumed.

Player-visible difference between the two cases:
  - dropping into the SAME lane -> DragDrop snaps the bomb back. Clear feedback.
  - dropping into a DIFFERENT lane -> DragDrop's guard does not fire, so
    _handleLaneDrop runs the full fly-into-the-lane animation and destroys the
    ghost (DragDrop.js:470-474) BEFORE GameLoop silently refuses. The bomb flies
    in, vanishes, nothing happens, and it is still sitting in the queue.

That second case is a FALSE SUCCESS, and "next to him" is exactly it — an adjacent
lane. Left unchanged as instructed; flagging it because a silent refusal that also
plays the success animation reads as broken even though the restriction is intended.

Shot window is SHOT_TRAVEL_TIME = 0.18s, shortened by the combo multiplier to
~0.06s at 2x — brief, but it is precisely the window a fast player is tapping in.
